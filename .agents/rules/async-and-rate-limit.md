# 异步、流式取消与资源限流规则

本文件只约束跨 Java/Python 的持久化任务、流式取消和 RAG 资源背压。处理这些路径时还必须读取对应端规则；系统状态与运行时关系仍以 `docs/architecture.md` 为准。

## 持久化任务

- Java 在同一 MySQL 本地事务中写入业务状态和任务，提交后才派发；投递成功不等于业务完成。
- 任务采用至少一次投递，以 `taskId`/`attempt` 幂等收敛。网络超时重投沿用当前 `attempt`，显式业务重试才递增。
- Java 拥有任务状态、重试资格、租约、恢复和最终裁决；Python 只拥有本次 RAG 执行结果与安全诊断。
- scheduler 通过数据库抢占、租约或乐观锁支持多实例恢复；进程内队列不得成为任务事实源。
- 删除或旧尝试到达执行端时必须安全拒绝或幂等清理，不能把迟到成功覆盖到较新的业务状态。

## 流式生成与取消

- 每次生成使用稳定 `generationId`；Java 通过 Nacos 选择 RAG 实例并在生成生命周期内保持实例亲和。
- 发起回答的流式方法不得持有覆盖 RAG HTTP/SSE 生命周期的数据库事务。问答记录的创建和每次状态裁决由独立 `QaRecordService` Bean 在各自短事务中完成，提交后才发起或继续外部流处理。
- 问答记录状态更新使用条件 SQL 防止终态被迟到事件覆盖；同一终态的重复事件幂等成功，Java Service 根据零行更新裁决幂等、终态冲突或记录缺失，Mapper 不拥有隐式状态机。
- SSE 事件必须来自根契约，Java 校验、转发并增量持久化，最终区分完整、拒答、已停止和未完成。
- 用户取消是显式业务命令，必须路由回原 RAG 实例；浏览器 abort、TCP 断开或 SSE EOF 都不能替代取消命令。
- 原实例不可达时，Java 关闭浏览器流、保存已有内容为已停止，并记录取消未确认；意外断流保存为未完成。
- V1 不创建跨实例活跃生成注册表。若未来无法维持实例亲和，先形成新的架构决策再引入协调机制。

## 背压与资源限制

- 一个 RAG 进程只加载一个模型并使用一个嵌入执行槽；不得用增加 worker 绕过显存和一致性约束。
- 查询队列优先且最多 5 个等待项；入库队列最多 1 个批次。达到上限时快速返回契约中注册的可重试忙碌错误。
- 队列长度、超时和并发限制必须集中配置并暴露安全指标；不得在 Controller、application 或 adapter 中散落不一致常量。
- 五路并发回答是系统验收目标，不表示允许五路并行嵌入。
- V1 不使用 Redisson、Redis Stream 或 Redis 分布式限流；不要把 RuoYi Redis 基础设施扩展成 RAG 任务总线。

## 验证

- 覆盖重复投递、乱序回调、租约过期、进程重启、旧 attempt、部分清理失败和显式重试。
- 覆盖浏览器 abort、显式取消、原实例不可达、SSE 意外断流以及终态持久化差异。
- 覆盖查询优先、两个队列溢出、忙碌错误重试属性、OOM/设备丢失撤销 readiness。
- 单端测试之外，运行 Java/Python 契约测试和经 Java HTTP/SSE 的系统验收。
