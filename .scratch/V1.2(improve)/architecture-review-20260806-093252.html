Problem

  • 9 个流式 ref 收敛一处；流相关 bug 的 locality 集中
  • index.js 成为真正的公开入口；页面不再直接 import 内部实现

2 · 加深问答记录 seam——隐藏持久化模型

Strong in-process

qarecord/service/QaRecordService.java · feedback/service/impl/FeedbackServiceImpl.java · feedback/domain/AdminFeedbackDetail.java · conversation/service/impl/ConversationServiceImpl.java

flowchart LR
  FB[FeedbackServiceImpl] -->|直接 import Mapper| QM[QaRecordMapper + RetrievalDiagnosticMapper]
  CV[ConversationServiceImpl] -->|findByGenerationId 返回 Entity| QR[QaRecordService]
  QR -.->|QaRecordEntity 泄漏出去| CV
  AD[AdminFeedbackDetail.from] -->|逐字段读取| RD[RetrievalDiagnosticEntity]
  classDef leak stroke:#dc2626,stroke-width:2px,color:#dc2626;
  class QM,RD,QR leak

Problem

问答记录能力没有自己的窗口，持久化模型却越界：FeedbackServiceImpl 是全模块唯一跨能力直接 import Mapper 的类；findByGenerationId 返回 QaRecordEntity；RetrievalDiagnosticEntity 被反馈 DTO 逐字段读取；共享诊断类型归属错了能力。

Solution

加深 seam：QaRecordService 提供意图化窄查询（requirePending、诊断快照值对象）；共享诊断类型归一个 owner；feedback 不再碰 Mapper 与 Entity。

Wins

  • 唯一一处跨能力 Mapper import 消失
  • 状态推导（status != STARTED）收敛进 qarecord
  • 持久化模型留在 seam 后，由 adapter 映射
  • 测试不再 new QaRecordEntity()；seam 成为测试面

3 · 把组合根从 Python transport 拆出去

Strong ports & adapters

ai-modules/services/rag/src/sage_vault_rag/transport/http/app.py · bootstrap/settings.py · adapters/milvus/store.py · adapters/bge_m3/embedder.py

before — app.py 同时是 transport + 安全 + 组合根

transport/http/app.py · 450 行

路由 + SSE 映射
4× verify_*（HMAC + 重放）— 复制粘贴
build_indexing / build_answering / build_cleanup
单进程 3× MilvusVectorStore
2× BgeM3Embedder — 模型加载两次

每个 builder 各自 new 依赖；GPU/内存翻倍。

after — bootstrap 拥有资源，transport 变薄

app.py

只留路由 + SSE 映射

bootstrap/composition.py · 深

拥有共享单例：1 embedder · 1 vector store · 1 generator
装配 indexing / answering / cleanup

verification.py

统一签名模块（见候选 4）

Problem

app.py 把组合根和安全层塞进 transport 层，违背其文档定位（"transport + contract mapping only"）。后果：单进程建 3 个 vector store 实例、bge-m3 模型加载两次——资源所有权散落在各 builder 函数里。

Solution

组合根挪到 bootstrap/composition.py，拥有共享单例；4 份 verifier 收进一个模块；app.py 只保留路由与 SSE 映射。

Wins

  • bge-m3 只加载一次，不再翻倍
  • 资源所有权单点——locality
  • 签名校验有唯一归属
  • transport/http 回归 transport-only

4 · 每端一个请求签名模块

Worth exploring ports & adapters

Java：DiscoveredRagAnswerAdapter · DiscoveredRagIndexingAdapter · DiscoveredRagCleanupAdapter · IndexingCallbackController · CleanupCallbackController · Python：transport/http/app.py（4× verify_*）

before — 同一契约事实的 9 份拷贝

Java ×5

HMAC canonical + sign
HMAC canonical + sign
HMAC canonical + sign
HMAC canonical + verify
HMAC canonical + verify + constantTimeEquals

Python ×4

verify_signature
verify_cancel_signature
verify_cleanup_signature
verify_indexing_signature

签名方案一改 = 9 处联动修改才能跨契约保持一致。

after — 每端一个模块

Java · RequestSigner

sign(secret, method, path, body, ts) — 所有 adapter 与回调 controller 共用

Python · verification.py

一个 verifier 供四条路由复用

契约测试指向该模块，而不是各调用点。

Problem

HMAC canonical/签名方案在 Java 复制 5 份、Python 复制 4 份（外加 2 份 constantTimeEquals）。它是跨端契约事实——今天格式一变需要 9 处联动改，漂移直到上线断链才暴露。

Solution

每端一个深签名模块，极简 interface，所有 adapter 与回调 controller 引用它；契约测试指向它。

Wins

  • 契约改动只改每端一处——locality
  • constantTimeEquals 去重
  • 签名可隔离测试

6 · RAG 失败分类统一一种语义

Worth exploring ports & adapters

application/indexing/service.py · application/cleanup/service.py · application/answering/service.py · model/privacy.py

before — 三套方案、两套语义

indexing → type(exc).__name__ → Java 诊断 （Python 类名跨契约泄漏）
cleanup → type(exc).__name__ → Java 诊断 （同样泄漏）
answering → 受控 privacy.classify_failure 词表

after — 一个分类器守在 seam

model/failure.py · classify

只输出注册错误码 + 安全的脱敏详情

indexing

cleanup

Problem

失败分类有三套实现、两种语义：indexing 和 cleanup 把 Python 异常类名明文写进发给 Java 的诊断，answering 却用受控词表。adapter 内部细节跨 wire contract 泄漏。

Solution

一个使用受控词表的失败分类模块，三条 application 路径共用；adapter 负责翻译，application 永不输出原始类名。

Wins

  • Python 内部细节不再跨契约泄漏
  • 统一一种可测的分类语义
  • locality：失败词表集中在一个模块

Top recommendation

先做 #1 —— 问答工作台流式生命周期模块

它位于仓库最热区域（近两个月每个迭代都改动 WorkspacePage.vue），是产品招牌行为，且目前前端零测试设施、完全不可测。它也正对应文档声明的目标结构（code-framework.md:239：conversations feature 拥有单活跃流生命周期）——所以这是在恢复既定意图，而不是发明新形状。加深后，下一次 UI 改动就会落在可测的 seam 上，回报持续累积。
